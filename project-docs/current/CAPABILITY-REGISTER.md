## The standing principle

> **PUBLIC CLAIMS MUST DESCRIBE THE CAPABILITY ACTUALLY PROVEN AND DEPLOYED, NOT THE ASPIRATIONAL
> HAZLENZ ARCHITECTURE.**

This is adopted as a product principle, not a style preference. The gap it guards is real and
currently wide: the deterministic HazLenz engine is deployed and governed; the Expert HazLenz
advisory layer has never been activated for a customer, has an unproven clarification verifier, and
sits on a hosted third-party model whose output was degenerate in 4 of 48 development executions.
A visitor reading "HazLenz AI" cannot distinguish those, and the register exists so that we can.

## Classification key

| code | meaning |
|---|---|
| `SUPPORTABLE_NOW` | Repository evidence supports the claim as written, today |
| `SUPPORTABLE_WITH_QUALIFICATION` | Supportable if scoped, dated or qualified in the copy itself |
| `NOT_CURRENTLY_SUPPORTABLE` | The evidence does not support it; using it today would overstate |
| `LEGAL_REVIEW_REQUIRED` | Turns on a legal question engineering cannot answer, whatever the evidence |

A claim can carry both a substantiation code and `LEGAL_REVIEW_REQUIRED`. Most do.

### D-030 — the controlled-beta decision this needs

Registered at §278 and **not remediated there**. Two options, and the product owner chooses:

* **A — add narrowly governed electrical coverage later**, with authoritative regulatory
  grounding and regression evidence, on the same footing as every other governed family.
* **B — explicitly limit and disclose unsupported electrical analysis** for the initial
  controlled beta.

**Option B has a sequencing consequence worth stating before it is discovered late.** The
disclosure would land in `../legal/PRODUCT-LIMITATIONS.md`, which is one of the seven artifacts
awaiting counsel review — so choosing B means that document changes **before** the review, not
after. `PRODUCT-LIMITATIONS.md` mentions no electrical limitation today.

Either way, the inspector's own "add a finding HazLenz missed" path remains available and was
verified present, so the condition is recordable by the person who observed it. The direction
of the defect is **under-surfacing on a family with no governed rule**, never a hazard asserted
without basis.

## F. Autonomy roadmap principle

Recorded as a product and architecture goal, adopted §156:

> **HazLenz should progressively reduce dependence on third-party reasoning providers while
> maintaining or improving demonstrated safety performance.**

The architecture aims for provider replaceability; bounded provider authority; HazLenz-controlled
validation; HazLenz-controlled governed knowledge; a deterministic fallback that always works; **no
third-party model as the final safety authority**; the ability to adopt self-hosted or open-weight
inference later if validated; and eventual self-contained HazLenz capability where technically and
legally appropriate.

Much of this is already built rather than aspirational, and that is worth stating precisely because
the register above is otherwise a list of things we cannot yet claim. `expert-provider.ts` names no
vendor, model, endpoint or credential — adapters translate and the core never learns a provider's
response shape, which is what makes replaceability real rather than promised. Expert output is
advisory by type and cannot become authoritative. Deterministic HazLenz runs and produces findings
whether or not any provider answers. §155's state model and §156's verifier contract both bound what
a provider is permitted to affect.

**Two constraints on this goal:**

1. **v1.0 must not be delayed solely until complete self-hosting exists.** The dependency is
   disclosed, bounded and replaceable; that is the correct v1.0 posture.
2. **Any future self-hosted model must meet the same or stronger safety-validation requirements as an
   external provider.** Running a model ourselves removes a contractual dependency. It removes no
   evidentiary obligation, and "we host it" is not a safety argument.

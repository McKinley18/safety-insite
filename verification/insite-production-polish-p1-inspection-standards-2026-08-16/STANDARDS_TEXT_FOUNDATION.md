# Authoritative Standards Text Foundation

## Starting state (per `insite-p1-remediation-2026-08-16/P1_STANDARDS_INTEGRITY_CONTRACT.md`)

- `standardText`/`plainLanguageSummary`-derived content shown as HazLenz's own summary (already honestly relabeled "HazLenz standard summary" in the prior P1 phase — preserved unchanged this phase).
- Genuine verbatim-text infrastructure existed but was fully disconnected: `RegulatorySection` entity + `RegulatorySyncService` (real eCFR/MSHA bulk-XML ingestion, live network calls to `govinfo.gov`) had **no migration** provisioning any of its backing tables, so the store had never been populated and nothing queried it.

## What this phase found on investigation

The gap was larger than previously documented: **five** related entities (`RegulatoryAgency`, `RegulatoryPart`, `RegulatorySubpart`, `RegulatorySection`, `RegulatoryParagraph`) were registered in TypeORM's entity list but **none** had a migration — not just `regulatory_section` as the prior report stated. All five are flat tables keyed by natural-key string columns (`agencyCode`/`titleNumber`/`part`/`citation`), with **no relational FK columns** between them — this made authoring a correct migration straightforward and low-risk (no cascade/relation semantics to get wrong).

## Work completed this phase

1. **Migration** (`1800000005800-RegulatorySectionCorpus.ts`): creates all 5 tables, matching the entity column definitions exactly (verified against the `.entity.ts` files, not guessed). Applied only to the disposable database `test_polish1_20260816`; the original `safescope` database was never touched.
2. **Real ingestion, verified**: called the pre-existing, unmodified `POST /regulatory/sync?part=1910` (OSHA) and `?part=56` (MSHA) endpoints, which fetch real bulk XML from `https://www.govinfo.gov/bulkdata/ECFR/...` — a live US government source, not AI-generated or hand-authored. 163 real OSHA §1910 sections and 422 real MSHA §56 sections landed with genuine verbatim text and full provenance (`agencyCode`, `titleNumber`, `part`, `section`, `citation`).
3. **Narrow data-quality bug found and fixed**: `RegulatorySyncService.syncRegulatoryPart()`'s paragraph-to-text join (`node.P.join(' ')`) stringified structurally-nested XML paragraph nodes (present when a paragraph contains inline markup, e.g. `<I>`) to the literal text `"[object Object]"` instead of their real content. Confirmed live on `29 CFR 1910.303`'s text before the fix; fixed with a small `paragraphText()` extractor that reads the XML text node's `_` field; re-ingested and confirmed clean, correct text after the fix. This is a data-extraction bug fix (extracting text that was already present in the real government source), not new content generation — no AI was used to write or complete any regulation text.
4. **Live wiring into the display path** (`canonicalWorkflowApi.ts` `getRegulatorySection()`, `SafeScopeStandardsSection.tsx` `StandardCitationHeading`): on-demand only — the lookup fires when the user clicks "Standard detail," never bundled into the classify/analysis payload (per the phase's performance-non-regression requirement). Fails soft to `null` on any error (offline, not-yet-ingested citation, auth lapse), so the panel always safely falls back to the existing honest "not currently available" message — the inspection is never blocked or made to look broken by this addition.

## Provenance model

Every displayed excerpt carries: agency (`OSHA`/`MSHA`), title/part/section, the exact citation string, and the source ingestion pathway (live govinfo.gov bulk XML via the existing connector — not a HazLenz-authored or AI-generated string). No summary text was ever copied into an authoritative-text field, and no authoritative text was ever generated by AI, per the phase's critical data rule.

## Section- vs. subsection-granularity, and the disclosure requirement

The corpus is **section-granularity** (e.g. `29 CFR 1910.303`), not paragraph/subsection-granularity (`RegulatoryParagraph` exists as a table but the sync path does not populate it). HazLenz frequently cites at subsection granularity (e.g. `29 CFR 1910.303(g)(2)(i)`). Per the phase brief's explicit instruction ("do not display a parent section when a more precise child subsection is cited unless the UI explicitly explains the scope"):

- `getRegulatorySection()` first attempts an **exact** citation match.
- If that misses, it strips the trailing subsection suffix and attempts a **parent-section** match.
- If the parent-section match succeeds, the UI renders an explicit amber disclosure banner: *"Showing the full text of [section] — this specific subsection ([citation]) is not separately available; the excerpt below covers the whole section."* This is always shown before the text, not silently.
- If neither matches, the existing honest "not currently available" message is shown — unchanged from the prior P1 phase.

## What remains deferred (`AUTHORITATIVE_TEXT_FOUNDATION_DEFERRED` for this subpart)

- **Paragraph/subsection-level ingestion** (`RegulatoryParagraph` population) was not attempted — `syncRegulatoryPart()` does not currently parse paragraph-level nodes into that table; doing so correctly (matching each subsection label like `(g)(2)(i)` to its own row) is a distinct parsing task with its own correctness risk, left for a dedicated follow-up rather than attempted hastily in this pass.
- **Full-corpus ingestion**: only OSHA §1910 and MSHA §56 were ingested (chosen because they cover the citations this session's own testing produced). Other parts (OSHA §1904/§1926, MSHA §46/47/48/50/57/62/77) are supported by the same connector/endpoint but were not run in this pass, to keep the live-network-call footprint proportionate to what was needed to prove and verify the feature.
- **`RegulatoryParagraph`/`RegulatorySubpart` tables**: created by the migration (for schema completeness, since they're part of the same registered entity set) but not populated by any ingestion run in this pass.

7. RETRY AND CALL-CEILING GOVERNANCE -- REQUIRED PRE-FREEZE ANALYSIS

   All eight questions answered from the code, not from the field names.

   (1) WHAT TRIGGERS A RETRY
       expert-runner.ts:95  if (!result.ok && isRetryableExpertFailure(result.kind))
       RETRYABLE  TIMEOUT, NETWORK_ERROR, HTTP_SERVER_ERROR, MALFORMED_JSON, TRUNCATED_RESPONSE, EMPTY_RESPONSE
       NOT        HTTP_CLIENT_ERROR, RATE_LIMITED, CREDITS_EXHAUSTED, SCHEMA_INVALID_STRUCTURED_OUTPUT, PROVIDER_REFUSAL, UNEXPECTED_MODEL_IDENTITY, PROVIDER_NOT_CALLABLE, NOT_CONFIGURED
       A boundary REJECTION (OUTPUT_REJECTED) is never retried, and neither is a refusal --
       "asking a model to re-answer a question it just answered unsafely is how a validator
       gets talked out of a refusal".

   (2) ARE RETRIES ENABLED ON THE PATH THE FORMAL HARNESS USES
       YES, and there is no flag that disables them. The harness calls runExpertAnalysis
       directly (expert-cohort-harness.ts:228), which is the permanent production runner.

   (3) MAXIMUM RETRIES PER LOGICAL CALL
       ONE. The runner performs at most two attempts and the ceiling is structural -- a
       single `if`, not a loop, so it cannot be raised by configuration.

   (4) DO RETRY REQUESTS COUNT AGAINST hardCallCeiling
       *** NO. THIS IS THE MATERIAL FINDING. ***
       expert-cohort-harness.ts:283  `accounting.callsAttempted + 1 > options.callCeiling`
       is evaluated ONCE PER ARM, before executeCall. executeCall then invokes
       runExpertAnalysis, which may issue TWO HTTP requests. `callsAttempted` and
       `providerInvocations` are both incremented ONCE per logical call.
       => callCeiling bounds LOGICAL CALLS. It does not bound billable provider requests,
          and no code path in the repository does.

       The §121 comment on RECOMMENDED_CALL_TOPOLOGY states the ceiling "covers a full retry
       on every planned call plus margin". That is FALSE about the mechanism. §133 inherited
       the error and reported that a 390-request worst case "would be stopped by the
       ceiling". It would not be. Both statements are corrected here.

   (5) DOES A RETRY REPLACE THE CALL OR ADD AN OBSERVATION
       It REPLACES it. runExpertAnalysis returns ONE ExpertRunResult per logical call and the
       harness pushes ONE CallRecord per arm. A retry produces no extra scored observation.
       `trace.attempts` records 1 or 2 -- but CallRecord does not carry it, so the attempt
       count is DISCARDED at the harness boundary.

   (6) DOES THE FROZEN PLAN PERMIT RETRIES
       It neither permits nor forbids them: expert-evaluation-plan.ts defines NO retry budget
       and NO ceiling formula. P4 requires an authorization naming "the cohort, the call
       count and the ceiling" -- singular, and it does not distinguish logical calls from
       billable requests. The distinction is unresolved in the frozen contract.

       M13_PROVIDER_CALLABILITY does address them, and its frozen denominator is
       "All attempted calls, every row, every repetition, RETRIES INCLUDED."
       scoreM13 counts one per CallRecord. Since attempts are discarded (5), M13 CANNOT be
       computed as its frozen contract specifies. This is a defect between contract and
       implementation, reported rather than repaired -- repairing scoreM13 would be a scorer
       change, which this operation is not authorized to make.

   (7) WHAT HAPPENS WHEN hardCallCeiling IS REACHED
       stopReason = CALL_CEILING_REACHED, the arm loop breaks, the row loop breaks, and the
       run returns what it completed. Remaining rows carry ZERO calls.

   (8) IS THE RUN INVALID, BLOCKED, OR MERELY INCOMPLETE
       MERELY INCOMPLETE at the harness, but that is not the end of it. Unanswered rows
       reduce every content measure's denominator, and the measurement contract makes a
       HARD_GATE with zero eligible opportunities UNMEASURED, which FAILS. So hitting the
       ceiling does not invalidate the run -- it silently converts it into a failing one.

   THE SPEND CEILING IS ALSO INERT, AND THIS IS A SECOND INDEPENDENT FINDING.
       harness:284 checks `accounting.spendUsd >= options.spendCeilingUsd` before each call.
       `spendUsd` accrues ONLY from `options.usageOf(callId)` (harness:289).
       A repository-wide search finds NO implementation of `usageOf` -- it is an optional
       hook and no caller supplies one. It therefore defaults to {0,0,0}, spendUsd stays 0
       forever, and the spend ceiling can NEVER fire.
       Consequence: M16_COST_PER_ROW would report $0.00/row, which the frozen contract
       requires to be "reported per run, never estimated".

       And even if usageOf were wired to the adapter, the adapter keeps only
       `this.lastTelemetry` (anthropic-expert-provider.ts:242), overwritten per HTTP request.
       A retried call would report ONLY the second attempt, silently undercounting the first
       billed request in both spend and M16.

   NET: NEITHER CEILING CURRENTLY BOUNDS PROVIDER SPEND.
       PLANNED_LOGICAL_CALL_COUNT        195
       MAXIMUM_BILLABLE_PROVIDER_REQUESTS 390   (one retry per call, unbounded
                                          by callCeiling = 200)

8. DERIVED PROVIDER-REQUEST CEILING OPTIONS

   The frozen plan defines no formula, so nothing is invented here. The options below are
   presented with their exact consequences; choosing among them is a product-owner decision.

   opt   ceiling  retries  max mean $  max worst $  consequence
   O1        195        0        6.19        20.28  exactly the planned calls, zero retry capacity
   O2        200        5        6.35        20.80  the existing 200, reinterpreted as a REQUEST ceiling
   O3        215       20        6.83        22.36  planned + a 10% global retry allowance
   O4        390      195       12.39        40.56  full theoretical one-retry-per-call maximum

   EXACT CONSEQUENCES, stated rather than scored:
     O1 (195)  the FIRST transient provider failure exhausts the budget and the run
              stops with rows unanswered, which becomes a FAILING evaluation per (8) above.
              Predictably fragile; the owner's own criterion rules this out.
     O2 (200)  tolerates 5 retried calls out of 195, i.e. a 2.6% transient-failure rate.
              §118 measured 18 of 18 calls succeeding, so 2.6% is not obviously too small --
              but 18 calls cannot characterise a rate at that resolution, and this number was
              chosen when the ceiling was believed to cover retries, which it does not.
     O3 (215)  tolerates a 10% transient-failure rate.
              This is the only option whose derivation matches the stated intent of the
              existing conservativeMaximumSpendUsd, which already carries a "10% retry-
              billing allowance". It reuses a number the programme already committed to
              rather than introducing a new one.
     O4 (390)  cannot be exceeded by construction, so it is the only option that
              never stops a run early -- but it authorises double the spend to protect
              against a failure rate nothing has measured. Not appropriate merely because it
              is the theoretical maximum.

   RECOMMENDATION (engineering, not a decision): O3. It is derived from an allowance the
   frozen cost model already states, it is the smallest option that is not predictably
   fragile, and it bounds spend at a figure below the existing recorded ceiling.

   EVERY OPTION REQUIRES CODE REPAIR BEFORE IT MEANS ANYTHING. A request ceiling cannot be
   enforced by a counter that increments once per logical call. At minimum:
     R1  count provider REQUESTS, not logical calls, against the ceiling (runner must report
         attempts to the harness; trace.attempts already exists and is discarded);
     R2  implement usageOf, or the spend ceiling stays inert and M16 reports $0.00;
     R3  accumulate adapter telemetry PER ATTEMPT, or a retried call under-reports its cost.
   R1 also happens to make M13's frozen denominator computable. None of these is authorized
   by this operation, and which of them is needed depends on the option chosen.

   R4 IS SEPARATE AND IS REQUIRED WHATEVER CEILING IS CHOSEN -- THE MODEL IS NOT BOUND.
     anthropic-expert-provider.ts:93  `model: process.env.EXPERT_ANTHROPIC_MODEL ||
     'claude-sonnet-5'`, and :224 `this.qualifiedModelIdentity = config.model`.
     The runner DOES refuse a response from an unexpected model -- but it compares the
     response against whatever the ENVIRONMENT said, not against the cohort's frozen
     identity. Setting EXPERT_ANTHROPIC_MODEL therefore silently reruns the formal cohort on
     a different model and the identity guard passes. The guard protects against a provider
     substituting a model; it does not protect against the operator doing so.
     REPAIR: the frozen manifest names the model, and the run asserts
     provider.qualifiedModelIdentity === manifest.model BEFORE the first request, refusing
     otherwise. This is what "do not inherit an environment-overridable model" requires.

# Critical finding: default inspection flow returned zero standards for every finding

## Status: FIXED and verified (unit regression + live Chromium, multiple rounds)

## Discovery

Found live, not by inspection of code first: a new end-to-end Chromium test inspection
("A technician is servicing the hydraulic baler and hazardous energy has not been isolated or
locked out...") produced a correctly-scoped, correctly-classified `lockout_tagout` finding with
`conditionState: ACTIVE`, but the Standard Detail panel read **"No standard established for this
finding yet."** for a textbook 29 CFR 1910.147 violation.

## Root cause

`evaluate()` in `backend/src/safescope-v2/evidence/evidence-foundation.ts` gates every single
jurisdiction-specific standards rule behind an **exact** match:

```js
const mine = e.jurisdiction === 'msha';
const gi = e.jurisdiction === 'osha-general-industry';
const construction = e.jurisdiction === 'osha-construction';
...
if (mine && servicing) output.push(decision(e, '30 CFR 56.12016', ...));
if (gi && servicing) output.push(decision(e, '29 CFR 1910.147', ...));
```

`buildEvidenceFacts()` in `shared-evidence-facts.ts` extracts `jurisdiction` as the literal string
`'unknown'` unless the request explicitly supplies a scope. The frontend's default inspection
"agency mode" is `"all"` (`frontend-next/app/inspection/page.tsx`: `useState("all")`), and
`getHazLenzScopesForAgencyMode()` maps `"all"`/unset to `scopes: undefined` on the wire — i.e. the
default, unmodified path **every new inspection takes** unless a user manually picks a specific
regulatory scope before running HazLenz.

Because `'unknown'` matches none of the three exact-jurisdiction checks, `mine`/`gi`/`construction`
were all `false`, so **every** jurisdiction-gated `if` block was skipped entirely — not one
candidate standard was ever produced for any finding, however unambiguous the violation, until a
user manually confirmed a jurisdiction. This is a hard, categorical false-negative on standards
matching in the default product configuration, not a low-confidence or honest-unknown result.

## Fix (three layers, all required to close the defect end-to-end)

1. **`evidence-foundation.ts` — `evaluate()`**: separated the rule-entry *gate* from the
   jurisdiction *predicate value*. `mineGate`/`giGate`/`constructionGate` proceed into a rule when
   jurisdiction is unconfirmed (not just when it's an exact match); `mineJur`/`giJur`/
   `constructionJur` report the jurisdiction predicate honestly as `UNKNOWN` (not falsely
   `CONTRADICTED`) when jurisdiction is merely unconfirmed. A confirmed *different* jurisdiction
   still yields `false` and still excludes the rule, exactly as before — only the previously
   unhandled "not yet confirmed" case changes. Result: an unconfirmed-jurisdiction observation now
   surfaces honest `UNKNOWN`/candidate standards (with jurisdiction listed as a missing predicate)
   instead of zero results.

2. **`shared-evidence-facts.ts` + `evidence-foundation.ts` — clarification-answer wiring**: the
   "Essential clarification" UI question "Can you confirm: general-industry jurisdiction?" (id
   `predicate-<citation>-<jurisdiction>-jurisdiction`, generated by `questionFor()`'s generic
   fallback) previously had no answer-handler at all — answering "Yes" did nothing. Added jurisdiction
   handling to the `clarificationAnswers` loop, and made `applyFindingScopedStandards()` forward
   `clarificationAnswers` and an explicitly-confirmed jurisdiction (from either
   `structuredObservation.jurisdiction` or a `confirmed` `jurisdiction` fact already present in
   `evidenceSnapshot.facts`) into each finding's own `buildEvidenceFacts()` call. Only the single,
   observation-wide `jurisdiction` fact is recovered this way — not the rest of
   `evidenceSnapshot.facts` — because jurisdiction cannot differ between findings in the same
   observation, whereas per-finding facts (guardState, fallExposure, etc.) forwarded wholesale would
   reintroduce the cross-finding leakage the finding-scoping fix (this session, phase 1) exists to
   prevent.

3. **`frontend-next/app/inspection-workspace/page.tsx` — multi-round answer accumulation**:
   `reanalyze()` previously sent only the single latest clarification answer on each round
   (`clarificationAnswers: clarificationAnswer ? [clarificationAnswer] : undefined`). Answering a
   second question on a later round silently dropped the first round's answer from the request,
   causing the already-answered jurisdiction question to reappear. Added
   `clarificationAnswerHistory` state that accumulates every answered `questionId` and resends the
   full history every round; `reanalyzeCurrentObservation()` (a fresh pass over revised text) resets
   the history.

4. **Unrelated but blocking**: `backend/src/main.ts` — the default Express JSON body-parser limit
   (100kb) started rejecting `POST /inspections/observations/:id/analyses` with `413 Payload Too
   Large` once findings began legitimately carrying multiple honest `UNKNOWN`-status
   `standardCandidates` (previously near-empty due to the defect above). Raised to `5mb` via
   `app.useBodyParser('json'|'urlencoded', { limit: '5mb' })`.

## Verification

- **Unit regression** (`backend/src/safescope-v2/tests/hazlenz-jurisdiction-unknown-standards-regression.ts`,
  11 assertions, wired into `hazlenz-core-regression.ts`): unknown-jurisdiction candidates surface
  as honest `UNKNOWN` (never fabricated `SUPPORTED`, never silently dropped); confirmed jurisdiction
  reaches `SUPPORTED`; confirmed *different* jurisdiction still fully excludes the sibling rule
  (no leakage introduced); clarification-answer "Yes" resolves a candidate to `SUPPORTED`; a
  jurisdiction confirmed on an earlier round is not forgotten on a later round.
- **Full regression suite**: `npx ts-node src/safescope-v2/tests/hazlenz-core-regression.ts` — only
  the two pre-existing baseline failures remain (Golden Hardening #7 "LOTO energized maintenance",
  Production Path "tagged but not locked"), unchanged before and after this fix; zero new
  regressions.
- **Live Chromium, single clean round-trip** (fresh inspection, observation: "A worker is servicing
  the stamping press and hazardous energy has not been isolated or locked out."):
  1. Initial analysis: Standard Detail panel shows **"CANDIDATE STANDARD — MORE EVIDENCE
     REQUIRED" / 30 CFR 56.12016 / MSHA energy control**, confidence Low, with the specific missing
     predicates listed — not "no standard established."
  2. Answered "Yes" to "Can you confirm: general-industry jurisdiction?": panel narrowed to a single
     remaining gap and swapped to **29 CFR 1910.147 / OSHA General Industry hazardous energy
     control** as the sole remaining candidate (MSHA sibling correctly dropped, not merely
     deprioritized).
  3. Answered "Yes" to the remaining "energized or capable" question: **PRIMARY STANDARD — 29 CFR
     1910.147**, Confidence **High**, "Why HazLenz selected this: HazLenz found submitted evidence
     supporting general-industry jurisdiction, servicing or maintenance activity, hazardous energy
     present or capable, energy not isolated and locked."
  4. Standard Detail expansion confirmed citation/title/HazLenz-explanation separation integrity:
     "OFFICIAL REGULATION TEXT: The verbatim text of 29 CFR 1910.147 is not currently available in
     HazLenz's local standards corpus. The summary below is a HazLenz-authored overview, not the
     official regulation language — consult the cited regulation directly for the verbatim
     requirement." No official-looking fabricated regulation text was presented at any point.

## Severity assessment

This was the dominant, systemic cause of low standards-recall in the default product
configuration — more severe than any single citation/title mismatch, because it suppressed
**all** jurisdiction-specific standards for **every** finding in **every** inspection that did not
explicitly pre-select a regulatory scope, which per the frontend's own default state
(`agencyMode = "all"`) is the common case. It directly contradicts the stated priority that HazLenz
"must return the correct standards for the actual finding" — a wrong-but-present candidate is a
correctness bug; a correct candidate silently withheld on every default-configuration inspection is
a product-wide functional failure of the standards feature.

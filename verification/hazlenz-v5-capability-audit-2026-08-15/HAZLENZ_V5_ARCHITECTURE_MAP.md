# HazLenz Architecture Map (as of `24e37703`)

This is a factual trace of the live `POST /safescope-v2/classify` pipeline — every stage identified was confirmed by reading the actual code, not inferred from directory/file names. Where a name suggested a capability that turned out to be dead, disconnected, or a placeholder, that is called out explicitly, because the directory-name layer of this codebase is **not a reliable guide to runtime behavior**.

## 0. The single most important fact about this system

**There is no LLM/AI model call anywhere in the HazLenz reasoning pipeline.** Confirmed by: no `anthropic`/`openai`/`@anthropic-ai/sdk`/langchain dependency in `backend/package.json`; zero matches for `anthropic|openai|chat.completions|messages.create|claude-|gpt-` across `backend/src`; no outbound HTTP client (axios/node-fetch/HttpService) used by any reasoning module; no API-key environment variable for any model provider. Every module with an "AI"-sounding name (`native-reasoning`, `brain/*`, `*-intelligence`, `reasoning-orchestrator`) is **deterministic, hand-authored TypeScript**: regex/keyword matching, static lookup tables, and rule trees, chained together and re-chained on each other's output. "HazLenz AI" is a large expert system, not a model-backed system, as of this snapshot.

This reframes several audit questions:
- Efficiency is a CPU/memory/maintainability problem, not a token-cost/model-latency problem (there is a documented production heap guard that silently degrades output under memory pressure — see §2).
- "Confidence" values cannot represent genuine model calibration; they are, without exception, hand-picked constants or step functions over keyword-match counts (see `HAZLENZ_V5_CAPABILITY_AUDIT.md` §9).
- The most consequential V5 architecture choice is whether/where to introduce an actual model call at all, and how to do that without touching the frozen V4 recognition core.

## 1. Two incompatible ways code gets "wired in" — read this before trusting any dead-code claim

The codebase uses two entirely different construction mechanisms:

1. **NestJS DI (`@Module` providers/controllers)** — the normal path for anything reachable via HTTP (`SafescopeV2Module`, `ApplicableStandardsModule`, `InspectionModule`, etc.). A service not listed in any `*.module.ts` is a reasonable candidate for "orphaned."
2. **A plain-`new` object graph rooted in `SafeScopeIntelligenceOrchestrator`**, which is itself lazily constructed with `new SafeScopeIntelligenceOrchestrator(...)` inside `safescope-v2.service.ts:1541-1547` (via dynamic `import()`, deliberately bypassing DI, apparently to defer its ~950-line constructor's cost). Its constructor `new`s ~60 more service classes directly (`orchestration/intelligence-orchestrator.service.ts:1-71` import list), several of which `new` further sub-services themselves (e.g. `MultiHazardDecompositionService` internally `new`s `HazardTaxonomyCoverageService`).

**A `grep` for a class name against `*.module.ts` produces false "orphaned" verdicts for anything in graph #2.** This was confirmed directly during this audit: `MultiHazardDecompositionService`, `HazardTaxonomyCoverageService`, `HazardInformationAbsorptionService`, and `ApprovedKnowledgeRetrievalOutputV1Service` are all live (imported and invoked from `intelligence-orchestrator.service.ts`) despite appearing in zero `.module.ts` files. The reverse is also true — some subdirectories under `safescope-v2/` genuinely are unreachable by either mechanism (e.g. `applicability-retrieval/`, `regulatory-brain/`, `hazard-universe/`, `standard-family-mapper/` as best determined — not exhaustively re-verified for every one of the 100+ subdirectories in this pass; a full live/dead census of graph #2 is itself a recommended V5-adjacent cleanup task, not something this audit fully completed).

**Practical implication for V5 planning:** before deleting or "cleaning up" any `safescope-v2/*` subdirectory, trace its actual construction chain from `safescope-v2.service.ts` and `intelligence-orchestrator.service.ts`, not just its `.module.ts` presence.

## 3. Duplicated reasoning / information loss identified

1. **Two parallel standards-applicability engines** (`ApplicableStandardsService` vs `StandardApplicabilityService`) reconciled by an ad hoc "governed citations" demotion rule. They can disagree on the same citation.
2. **Two parallel risk engines** (`risk-engine.ts` `evaluateRisk()` and `brain/risk-reasoning.service.ts`), both scoped to the single primary classification, never reconciled into one canonical risk value — both ship in the response.
3. **3-4 parallel corrective-action engines** (`ActionEngineService`, `CorrectiveActionBrainService`, `DefensibleCorrectiveActionService`, `SafeScopeCorrectiveActionReasoningService`) converging through ad hoc merge logic in `buildEnhancedGeneratedActions()`; one of them (`SafeScopeCorrectiveActionReasoningService`) self-labels `mode: 'deterministic_test_only_advisory'` yet runs in the live path and its output doesn't appear to merge into the final `generatedActions`.
4. **The same raw text is independently re-scanned by dozens of files** rather than deriving a shared fact set once: 115 files independently test for `"lockout"`, 126 for `"energized"`, 179 call `.toLowerCase()` on a text parameter (measured across `safescope-v2/`). No canonical "energy state" (or similar) fact is computed once and threaded through; every consumer re-derives it.
5. **A well-designed evidence-provenance type already exists** (`EvidenceFact.source`: `user_text | user_confirmation | photo_model | site_context | inspection_context | clarification | qualified_review | system_inference`, plus `FactStatus`) but is scoped to `evidence-foundation.ts`'s own predicate logic — the ~60 orchestrator engines derive conclusions directly from raw text via their own regex, bypassing this fact model entirely, so most conclusions in the response are **not** traceable to a specific `EvidenceFact`.
6. **A genuinely well-built control-hierarchy/effectiveness QA layer is dead code**: `SafeScopeActionQualityService` and `SafeScopeControlEffectivenessService` (real hierarchy-of-controls enforcement, `effective/partially_effective/interim_only/ineffective/insufficient_information` ratings) are instantiated but `.evaluate()` is never called anywhere in the repository.
7. **A literal placeholder stub ships in production output**: `CorrectiveActionControlMapService.mapControls()` is explicitly commented `// Placeholder implementation.`, ignores its inputs, and is invoked from the live orchestrator with literal dummy arguments (`'hazard'`, `'mechanism'`, `[]`) — its hardcoded output (`preferredControlFamilies: ['guarding']`, `weakActionsToAvoid: ['Be careful']`, etc.) is included in the response's `intelligence.controlMap`.
8. **`EvidenceQuestionGenerationService` (a TF-IDF question generator) and `JurisdictionApplicabilityDecisionTreeService`'s `reviewerQuestions`** are computed by the orchestrator but not obviously consumed downstream — likely dead output, not dead code.
9. **`EvidenceSufficiencyService`'s 9-dimension sufficiency scoring** is computed but not consulted by the actual finalize/continue decision (`resultStage`), which instead uses a separate hardcoded safety-decisive-question-ID allowlist.
10. **Re-analysis reruns the entire deterministic pipeline from scratch** on every clarification round — there is no `/reanalyze` endpoint, no incremental/partial recompute, and no caching; the only reuse is at the persistence layer (idempotency-key replay and content-hash finding reconciliation in `reconcileDecompositionFindings`), which happens *after* the full compute has already re-run.

## 4. Architectural bottlenecks

- `safescope-v2.service.ts` (7,122 lines, `classify()` alone ~3,900 lines) and `reasoning-orchestrator.service.ts` (2,961 lines) are both monolithic single-file/single-method implementations. This is a genuine maintainability and testability bottleneck independent of any AI-capability question — isolating or unit-testing one stage requires understanding the whole file.
- The `SafeScopeIntelligenceOrchestrator`'s ~60-service synchronous fan-out (§2, stage 8) runs unconditionally end-to-end for every request that isn't heap-guarded, even when only a subset of its output is used downstream — no lazy/conditional execution per sub-engine.
- The production heap guard (§2, stage 8) is a real operational bottleneck: under memory pressure, the entire "intelligence" layer is silently dropped in favor of a degraded response, with (as far as this audit traced) no field in the response contract that flags "this was a degraded evaluation" for the frontend/inspector to see.

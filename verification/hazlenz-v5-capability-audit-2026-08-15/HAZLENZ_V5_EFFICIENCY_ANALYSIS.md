# HazLenz V5 Efficiency Analysis

**Governing fact:** HazLenz has no LLM/model call anywhere in its reasoning pipeline (verified: no AI SDK dependency, zero matches for provider API patterns, no outbound HTTP client in any reasoning module — see `HAZLENZ_V5_ARCHITECTURE_MAP.md` §0). Every "expensive" thing this document identifies is CPU-bound, memory-bound, or database-I/O-bound work in a large deterministic TypeScript expert system — not token cost or model latency. Any efficiency plan aimed at "reducing model calls" would target something that doesn't exist here; the actual levers are compute redundancy, memory footprint, database round-trips, and inspector-perceived wait time.

## 1. Repeated / duplicated work within one request

- **The dominant redundancy**: the same `fusedText` string is independently re-scanned by dozens of separate services rather than deriving a shared fact set once. Measured: 115 files under `safescope-v2/` independently regex-test for `"lockout"`, 126 independently test for `"energized"`, 179 independently call `.toLowerCase()` on a text parameter. A single `classify()` call re-derives "is this locked out / energized / at height / near workers" dozens of times over, each with its own slightly-different regex, rather than computing one canonical fact and passing it down.
- **Two full risk computations per request** (`risk-engine.ts` `evaluateRisk()` and `brain/risk-reasoning.service.ts` `RiskReasoningBrainService`), structurally overlapping, never reconciled into one canonical value, both shipped in the response.
- **Two full standards-selection computations per request** (`ApplicableStandardsService` regex+DB scoring, and `StandardApplicabilityService`'s 44-rule pack), reconciled only by an ad hoc post-hoc demotion rule.
- **3-4 corrective-action generation passes per request** (`ActionEngineService`, `CorrectiveActionBrainService`, `DefensibleCorrectiveActionService`, and a fourth `SafeScopeCorrectiveActionReasoningService` self-labeled test-only-advisory but running live), merged in `buildEnhancedGeneratedActions()`.
- **No `JSON.parse(JSON.stringify(...))`-style literal re-serialization redundancy was found** — this is not a "we're wastefully round-tripping JSON" problem; it's a "we're wastefully re-deriving the same semantic facts via independent code paths" problem, which is architecturally deeper and not fixable by a quick serialization optimization.

## 2. Model/computation calls per request

Zero model calls (confirmed). The relevant analogue to "how many model calls" is: how many of the ~60 synchronous `.evaluate()` calls inside `SafeScopeIntelligenceOrchestrator.evaluate()` actually run per request, unconditionally, chained sequentially (each depending on prior outputs, so no parallelization opportunity without restructuring the dependency graph) — confirmed via direct reading of `orchestration/intelligence-orchestrator.service.ts`'s `evaluate()` body, ~60 `this.xEngine.evaluate(...)` calls, none awaited (none are async), each threading 3-6 prior results as input. This is pure CPU time on the request thread, proportional to observation text length and the number of active regex checks — the exact magnitude was not benchmarked in this audit (no profiling was run; this is a code-structure finding, not a measured-latency finding) but the *shape* of the cost (linear fan-out of independent regex-heavy passes over the same string) is confirmed.

## 3. Caching

**Effectively none.** Two static, disk-load-once caches exist (`HazardTaxonomyCoverageService`'s `cachedCoverageMap`, `ApprovedKnowledgeRegistrySearchService`'s `cachedRecords`/`cachedIndexes`) — both cache a static reference JSON file read off disk once per process, not classification results or repeated-input dedup. No `CacheModule`, no Redis/`ioredis` import anywhere in `backend/src`. Standards/knowledge-chunk database lookups are not cached — identical or near-identical observation text re-runs the full DB query + regex scoring from scratch every time, with no memoization keyed on (text hash, jurisdiction, classification).

## 4. Re-analysis efficiency

There is no dedicated `/reanalyze` endpoint or partial-recompute path — clarification-answer flow calls the exact same `classify()` again with `clarificationAnswers`/`priorStructuredObservation` merged in, and the **entire pipeline reruns unconditionally**: evidence fusion → classification → risk → reasoning orchestrator → knowledge routing → standards → decomposition → confidence → corrective actions → narrative, every single stage, even when the answered question could only possibly affect one or two downstream stages (e.g., answering "is the equipment locked out: yes/no" cannot change which hazard *family* was detected, only the energy-state fact and anything derived from it, yet decomposition and classification rerun anyway). The only reuse that exists is at the **persistence** layer, after the full recompute: `addAnalysis()`'s idempotency-key replay (skips a duplicate DB write for an identical repeated request) and `reconcileDecompositionFindings()`'s content-hash equality check (skips a spurious "finding materially changed" event when a rerun produces byte-identical output) — both are storage-layer dedup, not compute-layer dedup.

## 5. Production memory/heap behavior

`safescope-v2.service.ts:1495-1527` implements a real, live production guard: when running on Render (`renderRuntime`) and either a configured heap-limit env var is exceeded (`configuredRenderHeapLimitMb`) or `fullRenderIntelligenceDisabled` is set, the **entire ~60-service intelligence orchestrator is skipped**, replaced with `buildDegradedHazLenzIntelligence()`, which still produces classification/risk/standards/actions but skips decomposition, narrative, confidence governance, and everything else in that fan-out. This is a legitimate operational safety valve, but as traced in this audit, there is no field surfaced in the API response contract that flags "this response was degraded due to memory pressure" — an inspector or the frontend cannot currently distinguish a degraded response from a full one. This is as much a trust/transparency issue as an efficiency one.

## Five largest efficiency opportunities, prioritized by user-perceived impact

1. **Compute a shared structured-fact set once per request, per hazard.** Directly eliminates the dominant redundancy (§1) and is the same architectural move recommended for intelligence/provenance reasons (see `HAZLENZ_V5_CAPABILITY_AUDIT.md`, required architecture question). Highest combined impact: reduces CPU work proportional to the number of engines no longer independently re-scanning text (potentially dozens), and is a prerequisite for finding-scoped everything.
2. **Make the production heap-guard degradation visible in the response contract**, and consider whether the guard's trigger conditions can be made cheaper to avoid tripping it as often (e.g., because of the redundant work in §1) rather than only reactively degrading. This item is about correctness/trust as much as raw efficiency — a silent quality regression under load is worse than a slow response.
3. **Add caching for standards/knowledge-chunk lookups**, keyed on a normalized-text hash plus jurisdiction/classification. Directly reduces database round-trips and repeated regex-scoring work for the (plausibly common, in a real inspection workflow) case of similar observations at the same site/equipment.
4. **Make re-analysis incremental.** The most common interaction loop in the product (answer a clarification question → wait → get updated result) currently pays the full pipeline cost every time. Even a coarse version — skip re-running decomposition/classification when the answered question is tagged as not affecting hazard-family identity — would cut the common-case cost substantially and reduce inspector-perceived wait time on the interaction they'll repeat most often.
5. **Remove or fix confirmed-dead/placeholder computation** (`SafeScopeNativeReasoningService.evaluate()` never called yet the class is instantiated; `CorrectiveActionControlMapService`'s placeholder stub; `EvidenceQuestionGenerationService`'s apparently-unconsumed output; the disconnected `EvidenceSufficiencyService` score) — each of these pays real CPU cost for zero delivered value today. Lowest absolute impact of the five, but also the lowest-risk, fastest-to-fix, and a reasonable first PR before tackling the architectural items above.

**What NOT to prioritize:** micro-optimizing individual regex patterns, string operations, or object allocations within any single engine. The cost structure here is dominated by *how many times* semantically-equivalent work is repeated across ~60 engines, not by the efficiency of any one engine's implementation. Micro-optimization inside one of the 60 engines without addressing the fan-out redundancy would be a poor use of effort relative to items 1-5 above.

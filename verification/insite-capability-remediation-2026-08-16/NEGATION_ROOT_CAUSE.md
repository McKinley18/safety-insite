# Negation / Safe-State Root Cause

## Correction to the prior verification session's root-cause claim

The prior phase's `CAPABILITY_COMMERCIAL_IMPLEMENTATION_REPORT.md` identified `backend/src/safescope-v2/engine/deterministic-classifier.ts` as the negation-blind primary classifier. **This was a misdiagnosis.** That file is never imported or instantiated anywhere else in the codebase (confirmed by `grep -rl "DeterministicClassifier"` returning only its own file) — it is dead code. The classifier actually wired into the live path is `backend/src/safescope-v2/classifier/weighted-classifier.service.ts` (`WeightedClassifierService`), instantiated directly in `safescope-v2.service.ts:50` (`private classifier = new WeightedClassifierService();`) and invoked at `safescope-v2.service.ts:985`. Confirmed empirically: the API response's `explanation` field text ("HazLenz AI matched weighted {label} signals.") only exists as a string literal in `weighted-classifier.service.ts:526`, nowhere in `deterministic-classifier.ts`. An initial attempted fix against the dead file produced zero change in live behavior, which is what surfaced the misdiagnosis; that dead-code edit was reverted (`git checkout --` on that one file only) before the real fix was made.

## Actual mechanism

`WeightedClassifierService.classify()` scores ~40 hazard profiles (`HAZARD_TAXONOMY` in `backend/src/safescope-v2/taxonomy/hazard-taxonomy.ts`) by summing weighted term matches (`scoreSignals()`, `weighted-classifier.service.ts:30-45`), each of which was a plain `normalizedText.includes(term)` substring check — no negation awareness. On top of that base score sit ~40 hand-authored "guardrail"/"booster" adjustments (family-disambiguation heuristics accumulated over many prior bug-fix cycles, e.g. "Confined Space Guardrail," "Lifting & Rigging vs Electrical Guardrail") — several of these are themselves plain regex `.test()` calls against the full text with no negation awareness either, most notably `hasElectricalExposure` (`weighted-classifier.service.ts:283`, pre-fix), which gates a -45 penalty that's supposed to suppress the electrical family when no real electrical hazard is present but couldn't detect that "exposed," "energized," "conductor" etc. were sitting inside a negated clause.

Separately, several hazard families (electrical, machine guarding, falls) had **no representation at all** for common real-world safe-state closing language ("no deficiencies were noted," "no hazards identified," "clean and dry," "confirmed to prevent contact") — the taxonomy's `negativeSignals` list (a field that already exists for exactly this purpose, used elsewhere for family-disambiguation) was empty or narrow for these profiles, and the classifier has no general "this whole observation is a clean report" signal.

## Fix (backend, three files, all additive/narrow — no rewrite)

1. **`backend/src/safescope-v2/reasoning-orchestrator/negation-context.util.ts`** — extended the existing `hasNonNegatedTerm(text, term)` (already used elsewhere for evidence-fact negation, e.g. `evidence/shared-evidence-facts.ts`) with an opt-in `requireWordBoundary: false` mode, exposed as `hasNonNegatedSubstring()`. This preserves the original function's default behavior for its existing callers and adds substring-safe matching (so "conductor" still matches inside "conductors," preserving existing recall) for the new caller.
2. **`backend/src/safescope-v2/classifier/weighted-classifier.service.ts`**:
   - `scoreSignals()` (the shared scoring function used by every profile's strong/moderate/weak/context/negative signal lists) now requires `hasNonNegatedSubstring(normalizedText, term)` in addition to substring presence — the single, general, "earliest shared decision point" fix affecting all ~40 hazard profiles uniformly.
   - Added `testNonNegated()`, a small helper applying the same negation-window logic to the file's ad hoc boolean "evidence present" regex gates, checking every regex match occurrence (not just the first) so a hazard affirmed elsewhere in a mixed observation still counts.
   - Applied `testNonNegated()` to `hasElectricalExposure` and `hasDirectElectricalExposure`, the two gates directly responsible for the electrical false-positive.
   - Added a new, clearly-commented "Verified Effective Control" guardrail block (matching the file's existing style/pattern), applying a -60 penalty to `machine_guarding`, `falls`/`walking_working_surfaces`, or `loto_stored_energy` when the text describes a control (guard/guardrail/energy isolation) as explicitly installed/enclosed AND confirmed effective, with no competing failure/defeat language anywhere in the text. The failure-language check is a broad, safety-conservative gate — any hint of "missing/broken/loose/not verified/etc." anywhere disables the discount, so ambiguous evidence defaults to staying flagged.
3. **`backend/src/safescope-v2/taxonomy/hazard-taxonomy.ts`** — added a handful of generic safe-closing-phrase `negativeSignals` entries ("no deficiencies were noted," "no hazards identified," "clean and dry," "no trip hazards," "no unprotected fall exposure") to the `electrical`, `machine_guarding`, `walking_working_surfaces`, and `falls` profiles — the taxonomy's own existing mechanism for this exact purpose, not a new mechanism.

## What this does and does not fix

This is a confidence-calibration and evidence-quality fix, not a full switch to "no hazard" labels. Every previously wrong high-confidence (82-93%, "high," no-review-required) false positive found by the prior session now scores 25-52% ("low," human review always required per the existing `requiresHumanReview: confidenceBand !== "high"` rule) — see `NEGATION_ADVERSARIAL_MATRIX.md` for the full before/after table. The dangerous failure mode (a user trusting a confidently-wrong answer) is closed; a few cases still show the original family label at low confidence rather than flipping to an explicit "no hazard" state, which is an accurate reflection of a scoring system that surfaces candidates for review rather than a binary hazard/no-hazard classifier — consistent with how every result already routes through mandatory human review before any violation is finalized.

## Known remaining limitation

`testNonNegated()` and `hasNonNegatedSubstring()` operate on the whole fused observation text, not per-clause. A single very long, multi-topic observation where the same hazard family is both negated in one clause and legitimately ambiguous in another could in principle be misjudged; this was not observed in the adversarial matrix (which includes an explicit mixed positive/negated case that passed) but is a structural limitation worth flagging for a future clause-scoped rewrite, not something this narrow fix resolves.

# Database Efficiency Audit

## Measurement limitation — reported honestly
`backend/src/database/data-source.ts` does not have TypeORM query logging enabled for the running application (only the migration CLI path emits `query:` log lines, which was observed during Phase 0's migration run but is not representative of runtime request behavior). Enabling `logging: true` for this audit would have required editing production source (`data-source.ts`), which is explicitly disallowed for this pass. **Exact per-request query counts were therefore not measured** — this section reports what was traced from source and observed indirectly (via `/health`, response timing, and the security-audit-event writes visible in error logs) rather than fabricated numbers.

## What was observed indirectly
- The `EntitlementGuard` (invoked on every entitlement-gated request, including the core HazLenz `/safescope/analyze`-style calls) performs at least one DB read per request (`EntitlementService.hasFeature`, confirmed by the `invalid input syntax for type uuid: "1"` stack trace captured live in `ERROR_EMPTY_LOADING_AUDIT.md`, which shows the query executing and failing) and, on denial, one additional write (`this.securityAudits.save(...)`, visible directly in `entitlement.guard.ts:47-54`).
- `BillingService.getBillingStatus` performs its own separate DB read on a code path that fired during normal dashboard/billing-status polling (same stack-trace evidence).
- The classify endpoint itself (`/safescope-v2/classify`) does **not** appear to hit the database at all in the pure-classify path (source trace shows the ~50-engine orchestrator operating entirely on in-memory data plus the `standards_master` table lookup for citation content) — consistent with the sub-200ms warm latencies measured in `HAZLENZ_PERFORMANCE_BASELINE.md`, which would be harder to hit if a chain of sequential queries were involved.
- Finding save / finalize / risk-confirm actions in the canonical workspace each triggered a distinct network round-trip in the browser (visible via network-request inspection during the live walkthrough), implying at least one write per stage transition; exact query-per-write counts were not captured.

## Known risk areas from source review (not exercised to a live N+1 reproduction in this pass)
- **Repeated entitlement/account lookups**: because `EntitlementGuard` runs its own DB check per gated request rather than reading from request-scoped user context already attached by `JwtGuard`, any screen that fires multiple gated calls in quick succession (e.g., the inspection workspace's several sequential finding actions) is a plausible candidate for repeated, avoidable entitlement lookups — flagged as **NEEDS_CONSUMER_TRACE**, not confirmed.
- **Large serialized columns**: `riskSnapshot` (jsonb, added by V5-C01) and the corrective-action package saved via "Save to Cloud" are large enough that the latter alone exceeded Express's 100KB body limit (see `API_PAYLOAD_AUDIT.md`) — if that same payload shape is what gets written to a `jsonb`/text column on save, it is also a candidate for oversized row storage, not just an oversized HTTP body. **NEEDS_CONSUMER_TRACE.**

## Recommendation for a future pass
Add temporary, additive TypeORM query logging (or a request-scoped query counter) for one classify cycle, one finding-save cycle, one finalize cycle, and one report-generation cycle, then re-run this audit's Phase 22 with real counts. This audit could not do so without violating the no-code-modification constraint, and reports that gap explicitly rather than guessing numbers.
